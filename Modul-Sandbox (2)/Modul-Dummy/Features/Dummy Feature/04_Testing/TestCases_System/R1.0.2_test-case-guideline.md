## 1. Global structure and alignment

Use the unified style for new test cases. Prefer this default order:

1. Test Case Key
1. Notes
2. Preconditions (conditional)
3. Success Criteria (conditional)
4. Execution Scenario OR Execution Steps
5. Expected Results (conditional, only applicable when Execution Steps are applied)
6. Test Attachments (conditional)

## 2. Missing-information policy

If information is missing, do not guess mandatory content.

If the user cannot provide a non-mandatory detail, omit it cleanly or leave a clearly marked placeholder in a template. Do not fabricate values.

## 3. Test Case Key

`Test Case Key` is mandatory.

Rules:

- Place `Test Case Key` as the first section of each new test case.
- Test Case Key must start with [KEYSTART] and must end with [KEYEND] tags.
- Between the starting and ending tags the content must be built up by keywords, as separate [TAG]s, each of them enclosed in "[]" sections.
- Build the [TAG] parts based on known test level, device family and device type, feature name and folder context and test focus.
- Suggested [TAG] items:
[TEST_LEVEL] - for defining main aspect of the test case, by its relevant test level
[FAMILY_RELEVANCY] - for providing the target device family, or overall categorization
[DEVICE_RELEVANCY] - for defining the device relevancy within a family
[MAIN_FEATURE] - identifies the main (parent) feature, EPIC name or target product (e.g. Device under Test is an ES or TOOL, then apply its name), in a compact short form
[FEATURE] - identifies the current feature where test case belongs to, what is the object of the scenario
[TEST_CATEGORY/TEST_TYPE] - categorizes the test case by giving hint regarding the depth or duration of the execution
[CURRENT_TEST_TOPIC_&_LOCAL_COUNTER] - highlights the main purpose of the test scenario and outcome of it, in a very compact way, for similar test cases a numbering is expected at the end in order to differentiate these instances. In case of negative tests, the negative outcome can be also hinted in a short form, e.g. EXAMPLE_TITLE_REJECTED or EXAMPLE_TITLE_NEGATIVE_TEST or FAILED_EXAMPLE_TITLE

- Within the same folder/category, for similar test cases the test keys must be increased sequentially by LOCAL_COUNTER part.
- When key is already exitsing, continue numbering without gaps when adding the next test in the same folder.
- Every alphabetic character within the Test Case Key must be capital in order to prevent searching mismatches caused by uppercase and lowercase differences.
- Avoid of using spaces or tabs, apply "-" or "_" characters instead of them.
- Keep the key unchanged across revisions of the same test case.
- Do not leave this field blank, and do not reuse keys from other test cases.
- The key must be unique.
- Required minimal pattern: `[KEYSTART][TEST_LEVEL][DEVICE_RELEVANCY][FEATURE][CURRENT_TEST_TOPIC_&_LOCAL_COUNTER][KEYEND]` (for example of Integration test related test case, which is applicable for ET200 decentralized system in general, belongs to Secure Firmware Download feature, for Upgrade and Downgrade combinations: `[KEYSTART][ITEST][ET200][SECURE_FIRMWARE_DOWNLOAD][UPGRADE_DOWNGRADE_TESTS][KEYEND]`).
- Recommended maximal pattern: `[KEYSTART][TEST_LEVEL][FAMILY_RELEVANCY][DEVICE_RELEVANCY][MAIN_FEATURE][FEATURE][TEST_CATEGORY/TEST_TYPE][CURRENT_TEST_TOPIC_&_LOCAL_COUNTER][KEYEND]` (for example of System test related test case, which is applicable for ET200 decentralized system, relevant for both IM and IO devices, belongs to CRA's Secure Firmware Download feature and being a Functional test which is also an Endurance test, for Upgrade and Downgrade combinations: `[KEYSTART][SYSTEST][ET200][IM][IO][CRA][SECURE_FIRMWARE_DOWNLOAD][FUNCT][ENDT][UPGRADE_DOWNGRADE_TESTS][KEYEND]`.

## 4. Notes

`Notes` is mandatory. Include these subsections:

### General Information

Mandatory. Add at least one meaningful sentence that explains the test purpose, goal, or context. Include applicability hints if the case only matters for certain products, families, or situations.

### Background Information

Optional. Add deeper purpose, insights from internal communication or documentation, bug references, problem reports, or work items when they explain why the test exists or why behavior changed.

### References

Optional. Cite requirement documents, concepts, tables, SPH chapters, and similar sources. Prefer document title plus chapter or page, and include a stable link when available. If there are multiple items, use a numbered list so later text can refer to reference numbers.

### Automation Information

Mandatory as a group. Always define `Test Automation Level` as one of:

- `Automated (full)`
- `Automated (partial)`
- `Manual`
- `Manual (not automatable)`
- `Manual (has automated equivalent)`
- `Not Relevant`

Add the following only when the test is `Automated (full)` or `Automated (partial)`:

- `Test Automation Environment`: summarize the automation environment and link to stable team or tool documentation.
- `Test Automation Reference(s)/ID(s)`: give unique script identifiers, git references, or exact automation links. Use numbered lists when there are several items.
- `Test Automation Parameter`: document only the parameters that materially affect execution or result interpretation. Prefer clear parameter names, referenced files, or file-and-key notation.

Parameter guidance:

- Explain only the parameters that matter for this case, not every possible script input.
- If parameters live in files, cite the file and key path, for example `HW_RACK.XML/CPUType`.
- If a test manager selects predefined parameter sets in a tool, mention the relevant parameter set behavior and which selection matters for the case.

### Author/Contact

Mandatory. Use the person's email address, for example `Author: jane.doe@example.com`. Add more author or contact people when helpful. If someone is no longer available, keep the entry and strike it through instead of deleting it.

### Estimated duration

Mandatory. Use logical and standardized units.

Allowed units and patterns:

- Preferred units: `s`, `m`, `h`, `cw`, `mo`
- Manual estimates often use ranges such as `<=1 m`, `<=5 m`, `<=30 m`, `<=1 h`
- Automated or long-running tests can use exact or threshold values such as `1 h`, `24 h`, `>48 h`

Rules:

- Display simply `Execution` whenever `Automated (full)` level or any `Manual` variant is applied, because the main goal is to keep this parameter as simple as possible.
- Separate `Execution (manual part)` from `Execution (automated part)` whenever `Automated (partial)` level is applied, since in this case both effort types could be relevant. By adding the word "part" it is intentionally highlighted that these values are not in OR relation (not "executing manually 1 hour" OR "executing automatically 10 mins" as an alternative to each other), but being AND relation (total execution effort is: "1 hour manual + 10 minuntes automated running"=1 hour 10 minutes)
- Manual duration includes the tester effort to start, stop, and evaluate the case, but not long asynchronous preparations shared across many cases. Relatively long execution (>= 4 hours) is too much for a single functional test case!
- Exploratory tests may require significant preparation time because the environment is usually single-use, in this case `Preparation` and `Execution` effort labels can be applied separately. Relatively long execution (>=4 hours...<=8 hours>) is acceptible for a single explorative test case!
- Some special endurance or automated tests may require significant evaluation time, in this case `Execution` and `Evaluation` effort labels can be applied separately.
- If duration depends on test phase, show multiple automated values clearly, for example `2 h/4 h/8 h [AT/RT/MT]`.

Avoid:

- `1 d`
- `1 w` or `1 wk`
- `1 m` when it could mean month instead of minute

## 5. Preconditions

Add `Preconditions` only when the execution requires explicit setup information. Organize content into these conditional groups:

### System Configuration

Describe the essential core setup: required modules, stations, CPUs, topology, interfaces, communication parameters, and necessary wiring of SIMATIC components.

Version guidance:

- Prefer minimal versions or future-proof wording instead of fragile hard-coded versions.
- If latest official or latest under-development version is required, state that expectation explicitly.
- Prefer generalized references to living documentation when environments change frequently.

### Hardware and Environmental Requirements

Describe special or external equipment, environmental constraints, power supply, network infrastructure, measurement devices, chambers, or other external dependencies.

### Automation and Tools

For automated cases, describe the required automation environment and any developer or official tools, including minimal versions and stable reference links where possible.

## 6. Success Criteria

Add `Success Criteria` when one or more expectations apply across the whole scenario and would otherwise be duplicated in many expected-result entries.

Use it for:

- common rules across steps
- thresholds or tolerances
- always-valid behavioral expectations
- positive or negative general conditions

Rules:

- If `Success Criteria` exists, the tester must satisfy both the success criteria and the per-step expected results.
- If the tooling does not support a separate section, put the common rule once at the start of the scenario, for example as the first step.
- Do not repeat the same cross-step expectation in every expected-result entry if one shared statement is enough.
- Try to write the entire `Success Criteria` content as one sentence.
- If this is not feasible, multiple sentences are allowed, but keep them concise.

## 7.A Execution Scenario

For describing the execution scenario and its steps there are two options defined.
"EXECUTION_SCENARIO_OPTION_#1" (for "test steps" combined with their "expected results") and "EXECUTION_SCENARIO_OPTION_#2" (for "execution steps" and "expected results" as two separated sections). Unless there is an exact requirement arrives for especially separate the "execution steps" and "expected results", "EXECUTION_SCENARIO_OPTION_#1" is the default option to be applied during test case designing.

Applying at least "EXECUTION_SCENARIO_OPTION_#1" or "EXECUTION_SCENARIO_OPTION_#2" is mandatory. When "EXECUTION_SCENARIO_OPTION_#1" is applied `Execution Scenario` section is mandatory (includes the steps and their results commonly), so further `Execution Steps` and `Expected Results` sections must be not applied.

Rules:

- The special section marker comments (<!--AGENT-ONLY_HINT!_MUST_BE_NOT_PART_OF_THE_READABLE_OUTPUT:START_EXECUTION_SCENARIO_OPTION_#1-->,<!--AGENT-ONLY_HINT!_MUST_BE_NOT_PART_OF_THE_READABLE_OUTPUT:END_EXECUTION_SCENARIO_OPTION_#1-->,<!--AGENT-ONLY_HINT!_MUST_BE_NOT_PART_OF_THE_READABLE_OUTPUT:START_EXECUTION_SCENARIO_OPTION_#2-->,<!--AGENT-ONLY_HINT!_MUST_BE_NOT_PART_OF_THE_READABLE_OUTPUT:END_EXECUTION_SCENARIO_OPTION_#2-->) must be never included in the generated final test case descriptions!
- Number every step uniquely.
- Every step must start after its number with label `[Test Step]`.
- Keep each step short, precise, reproducible, and free from ambiguous abbreviations.
- Do not represent the main scenario as unordered bullets.
- For manual cases, keep the number of steps as low as reasonably possible; around 15+ steps is already a warning sign.
- Automated scenarios may be longer, but keep debugging and evaluation practicality in mind.
- In `Automated (partial)` cases, explicitly mark which steps are automated.
- If a setup is intentionally freely selectable, require the tester to document the final chosen setup so the executed case stays reproducible.
- When the tooling supports step names, keep the sequence number visible in the name.
- Generalize or branch steps by phase, family, or product when that improves reuse and avoids duplication.
- Every step must have an own `[Expected Result]` section.
- State the expected result, state, comparison value, or outcome clearly.
- Never leave an expected result blank. If nothing visible changes, say `No change is expected.` or `No specific expected result.`
- When outcomes depend on family, category, environment, or device type, branch them explicitly inside the result.
- Insert a literal TAB character (U+0009) immediately before every occurrence of `[Expected Result]` label, while preserve original formatting between current step number and `[Test Step]` label.
- Insert an HTML `<br>` immediately after every occurrence of `[Test Step]` and `[Expected Result]` labels.

## 7.B Execution Steps

For describing the execution scenario and its steps there are two options defined.

If there is an exact requirement arrives for especially separate the "execution steps" and "expected results", "EXECUTION_SCENARIO_OPTION_#2" must be applied during test case designing.

When "EXECUTION_SCENARIO_OPTION_#2" is applied `Execution Steps` and `Expected Results` sections are mandatory (includes the steps and their results separately), so further `Execution Scenario` section must be not applied.

- Number every step uniquely.
- Keep each step short, precise, reproducible, and free from ambiguous abbreviations.
- Do not represent the main scenario as unordered bullets.
- For manual cases, keep the number of steps as low as reasonably possible; around 15+ steps is already a warning sign.
- Automated scenarios may be longer, but keep debugging and evaluation practicality in mind.

Automatic changing of "EXECUTION_SCENARIO_OPTION" format:

- When "EXECUTION_SCENARIO_OPTION_#2" is applied (because it is required), but the execution scenario is too long (e.g. >>15+ steps), it is advised to automatically switch to "EXECUTION_SCENARIO_OPTION_#1" in order to provide best readability.

## 8. Expected Results

When "EXECUTION_SCENARIO_OPTION_#1" is applied, `Execution Steps` and `Expected Results` sections must be not applied.

When "EXECUTION_SCENARIO_OPTION_#2" is applied `Execution Steps` and `Expected Results` sections are mandatory.

Rules:

- Every Execution Step item must have an Expected Results item counter-part.
- Map each result to its step through the same sequence number.
- State the expected result, state, comparison value, or outcome clearly.
- Never leave a result blank. If nothing visible changes, say `No change is expected.` or `No specific expected result.`
- When outcomes depend on family, category, environment, or device type, branch them explicitly inside the result.

## 9. Attachments

`Test Attachments` is conditional.

Use attachments only when a reference or link is not enough. Good candidates are:

- configuration matrices that do not fit well in text
- report or measurement templates
- generalized support material that improves execution

Avoid attachments when they create maintenance or access problems.

Rules:

- Prefer textual references or stable links when they are sufficient.
- Include document titles and chapter references together with links so the reference remains usable if the link later breaks.
- Do not upload sensitive or restricted material when a text reference would be safer.
- Avoid frequently changing attachments that reduce long-term reusability.
- Ask whether images should be linked or attached when screenshots, setup photos, diagrams, matrices, or plots would improve understanding.
- In Markdown, reference each image with a short explanation of what it shows and why it matters for setup, execution, or evaluation.

## 10. Final checklist

Before you finish a test case, confirm all items below:

- `Test Case Key` exists and follows `[KEYSTART][TEST_LEVEL][FAMILY_RELEVANCY][DEVICE_RELEVANCY][MAIN_FEATURE][FEATURE][TEST_CATEGORY_OR_TYPE][CURRENT_TEST_TOPIC_&_LOCAL_COUNTER][KEYEND]` pattern, where starting with `[KEYSTART]` and ending with `[KEYEND]` is verified and `[CURRENT_TEST_TOPIC_&_LOCAL_COUNTER]` is unique in the current folder! Test Case Key example `[KEYSTART][SYSTEST][ET200][IM][IO][CRA][SECURE_FIRMWARE_DOWNLOAD][FUNCT][ENDT][UPGRADE_DOWNGRADE_TESTS][KEYEND]`).
